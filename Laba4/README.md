# Лабораторная работа №4 — Механизмы синхронизации (параллельный поиск через Pipes)

## 1. Задание

> Разработать программу, которая выполняет параллельный поиск телефонных адресов из предыдущей
> задачи и формирует отчет. Данные для поиска берутся из текстового файла. Результаты поиска
> (отчет) помещаются в текстовый файл. Параллельный поиск должен выполняться в нескольких потоках.
> Распределение данных по рабочим потокам и сбор результатов следует выполнять через трубы (Pipes).

## 2. Файлы

| Файл | Что внутри |
|---|---|
| `main.cpp` | Вся программа (WinAPI): потоки, трубы, критические секции, отчёт |
| `queries.txt` | Входные данные: по одной строке поиска на строку |
| `report.txt` | Выходной отчёт (создаётся программой) |
| `build.bat` | Сборка под Windows: `PhoneDb.dll` из `..\Laba2\phonedb.cpp` + `Laba4.exe` |
| `Makefile` | То же самое с Linux через MinGW, запуск `wine Laba4.exe` |

**Связь с ЛР2:** поиск делает та же DLL-библиотека `PhoneDb.dll` (функции `DbOpen`, `DbLoadFromText`,
`DbSearch`), собранная из исходников `../Laba2`. Данные загружаются из `../Laba2/phones.txt`.
Поэтому папка `Laba4` должна лежать рядом с `Laba2`.

## 3. Сборка и запуск

```cmd
build.bat
Laba4.exe
```
Затем открыть `report.txt`.

## 4. Как это устроено

```
                       труба 1
                   ┌──────────────► [поток 1] ─┐
 queries.txt ──► [главный поток]    труба 2    │       общая труба
                   ├──────────────► [поток 2] ─┼──────────────────► [поток-сборщик] ──► report.txt
                   │   ...                     │   (под критической
                   └──────────────► [поток 4] ─┘     секцией)
```

### Шаги `main()`

1. **Открывает БД из ЛР2** (`DbOpen` — проецирование файла в память) и при необходимости
   загружает `phones.txt`.
2. **Читает запросы** из `queries.txt` в массив строк.
3. **Создаёт общую трубу результатов** `CreatePipe(&g_resultRead, &g_resultWrite)`
   и поток-сборщик `CollectorThread`.
4. **Создаёт 4 рабочих потока**, у каждого своя труба заданий (`CreatePipe`).
5. **Раздаёт запросы по кругу:** запрос `i` пишется в трубу потока `i % 4`
   (сообщение `TaskMsg` = номер запроса + строка).
6. **Закрывает пишущие концы труб заданий.** Для рабочего потока это сигнал «данных больше
   не будет»: `ReadFile` возвращает ошибку, цикл заканчивается, поток завершается.
   Главный поток ждёт их всех: `WaitForMultipleObjects(4, threads, TRUE, INFINITE)`.
7. **Закрывает пишущий конец общей трубы** → сборщик дочитывает остаток и тоже завершается
   (`WaitForSingleObject`).
8. **Записывает отчёт** `report.txt` по порядку запросов.

### Рабочий поток (`WorkerThread`)
```
пока ReadExact(своя труба, задание):        ← блокируется, пока нет задания
    n = DbSearch(запрос)                     ← поиск из DLL ЛР2
    сформировать текст результата
    EnterCriticalSection
        записать заголовок + текст в общую трубу
    LeaveCriticalSection
```

### Поток-сборщик (`CollectorThread`)
```
пока ReadExact(общая труба, заголовок):
    прочитать текст (заголовок говорит, сколько байт)
    положить в g_results[номер запроса]
```
Результаты приходят **вперемешку** (кто быстрее), но каждый кладётся на своё место по номеру
запроса, поэтому отчёт получается упорядоченным.

## 5. Механизмы синхронизации в программе

| Механизм | Где | Зачем |
|---|---|---|
| **Анонимные трубы** (`CreatePipe`, `ReadFile`, `WriteFile`) | раздача заданий и сбор результатов | передача данных между потоками; `ReadFile` на пустой трубе **блокирует** поток, пока нет данных — сама труба синхронизирует производителя и потребителя |
| **Закрытие трубы** (`CloseHandle`) | шаги 6 и 7 | сигнал «конец данных» — поток выходит из цикла чтения |
| **Критическая секция** `g_resultLock` | запись в общую трубу | 4 потока пишут в одну трубу; сообщение = заголовок + текст (два `WriteFile`), без блокировки куски разных потоков перемешались бы |
| **Критическая секция** `g_printLock` | `printf` | чтобы строки на консоли не перемешивались |
| **`WaitForMultipleObjects`** / **`WaitForSingleObject`** | конец `main` | ждать завершения потоков (объект «поток» переходит в сигнальное состояние, когда поток завершён) |

## 6. Что показать на защите

1. Запустить `Laba4.exe`. На консоли видно, какой запрос отправлен какому потоку, и что
   потоки выполняют их **не по порядку** — параллельно.
2. Открыть `report.txt` — для каждого запроса указан поток и найденные записи.
3. Можно дописать свою строку в `queries.txt` (например, `Кирова`) и запустить снова.

## 7. Вопросы и ответы

**Что такое труба (pipe)?**
> Объект ядра — канал с двумя концами: в один пишут (`WriteFile`), из другого читают (`ReadFile`).
> Данные идут в порядке записи (FIFO). `CreatePipe` создаёт анонимную трубу и возвращает два дескриптора.

**Как поток узнаёт, что заданий больше нет?**
> Главный поток закрывает пишущий конец его трубы. Когда все данные прочитаны и пишущих концов
> не осталось, `ReadFile` возвращает `FALSE` (`ERROR_BROKEN_PIPE`) — поток выходит из цикла.

**Зачем функции `ReadExact` / `WriteExact`?**
> Труба — поток байтов. `ReadFile` может вернуть меньше байт, чем запрошено, поэтому читаем в
> цикле, пока не наберём целое сообщение.

**Почему у каждого рабочего своя труба заданий, а труба результатов одна?**
> Так главный поток сам решает, кому какой запрос отдать (распределение). Результаты же удобно
> собирать в одном месте — одному сборщику достаточно читать одну трубу. За то, чтобы
> несколько писателей не мешали друг другу, отвечает критическая секция.

**Почему сначала ждём рабочих, и только потом закрываем `g_resultWrite`?**
> Рабочие пишут в этот дескриптор. Если закрыть его раньше, их `WriteFile` завершится с ошибкой
> и результаты потеряются.

**Не будет ли взаимной блокировки (deadlock)?**
> Нет: сборщик работает отдельным потоком и всё время читает трубу результатов, поэтому
> рабочие никогда не застрянут на записи, а значит, и главный поток не застрянет на раздаче.

**Безопасно ли вызывать `DbSearch` из нескольких потоков одновременно?**
> Да: потоки только **читают** базу, а все временные буферы `DbSearch` локальные (на стеке потока).
> У каждого рабочего потока свой массив результатов `found`.
