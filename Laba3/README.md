# Лабораторная работа №3 — Многозадачность (ThreadPool)

## 1. Задание

> Разработать переносимый (portable) класс ThreadPool. Объект этого класса содержит несколько
> потоков, находящихся в состоянии ожидания. К объекту можно обратиться с запросом выполнить
> некоторый метод некоторого объекта в потоке. Для выполнения процедуры объект класса ThreadPool
> подключает поток из пула ожидающих потоков.
> (Доп. задание: класс ThreadPool должен работать на Windows и Linux).

## 2. Файлы

| Файл | Что внутри |
|---|---|
| `threadpool.h` | Весь класс `ThreadPool` + маленький слой `os::` с вызовами WinAPI / pthreads |
| `main.cpp` | Демонстрация: пул из 3 потоков выполняет 8 вызовов методов двух разных классов |
| `build.bat` | Сборка под Windows (MinGW g++) → `Laba3.exe` |
| `Makefile` | `make` — сборка `Laba3.exe` с Linux (кросс-компилятор, запуск через `wine`); `make linux` — Linux-версия |

## 3. Сборка и запуск

```cmd
build.bat
Laba3.exe
```

## 4. Как это устроено

### 4.1. Переносимость — слой `os::`

Основная реализация сделана на **WinAPI**. Всё, что зависит от ОС, собрано в начале `threadpool.h`
в пространстве имён `os` и выбирается препроцессором (`#ifdef _WIN32`):

| Что | Windows (WinAPI) | Linux (POSIX) |
|---|---|---|
| Поток | `CreateThread`, `WaitForSingleObject` | `pthread_create`, `pthread_join` |
| Мьютекс | `CRITICAL_SECTION` (`EnterCriticalSection` / `LeaveCriticalSection`) | `pthread_mutex_t` |
| Условная переменная | `CONDITION_VARIABLE` (`SleepConditionVariableCS`, `WakeConditionVariable`) | `pthread_cond_t` |

Сам класс `ThreadPool` вызывает **только** `os::Lock`, `os::CondWait`, `os::StartThread` и т.д.,
поэтому его код один и тот же для обеих систем. Чтобы перенести его на другую ОС, достаточно
переписать ~15 коротких функций в `os::`.

### 4.2. Устройство пула

```
            Run(&obj, &Класс::Метод)
                     │
                     ▼
   ┌───────── очередь задач (std::queue) ─────────┐   ← защищена мьютексом
   │  [задача] [задача] [задача] ...              │
   └──────────────────────────────────────────────┘
          │ CondSignal(hasTask) — «разбудить один поток»
          ▼
   поток 1 (спит)   поток 2 (работает)   поток 3 (спит)
```

1. **Конструктор** `ThreadPool(3)` создаёт 3 потока. Каждый поток сразу засыпает на условной
   переменной `hasTask` — это и есть «состояние ожидания» из задания (поток не тратит процессор).
2. **`Run(obj, &Класс::Метод, аргумент)`** упаковывает вызов `obj->Метод(аргумент)` в объект
   `std::function` (через лямбду), кладёт в очередь и будит **один** ждущий поток.
3. Проснувшийся поток **под мьютексом** забирает задачу из очереди, отпускает мьютекс
   и выполняет её. Потом снова засыпает.
4. **`Wait()`** ждёт на второй условной переменной `allDone`, пока очередь не опустеет и
   ни один поток не будет занят (`busy == 0`).
5. **Деструктор** ставит флаг `stopping = true`, будит **все** потоки (`CondBroadcast`)
   и дожидается их завершения (`JoinThread`).

### 4.3. Почему `CondWait` стоит в цикле `while`, а не в `if`

```cpp
while (tasks.empty() && !stopping)
    os::CondWait(&hasTask, &mutex);
```
Поток может проснуться, а задачу уже забрал другой поток (или пробуждение «ложное» —
так бывает и в Windows, и в Linux). Поэтому после пробуждения условие проверяется ещё раз.

### 4.4. Зачем `WorkerEntry` статический

ОС (`CreateThread` / `pthread_create`) умеет запускать только обычную функцию с параметром `void*`,
а не метод класса. Поэтому передаём `this` как параметр, а статическая функция `WorkerEntry`
вызывает `((ThreadPool*)self)->WorkerLoop()`.

## 5. Что показать на защите

Запустить `Laba3.exe`. В выводе видно:
- у задач **разные id потоков**, но всего их 3 — потоки **переиспользуются**;
- одновременно начато не больше 3 задач: 4-я начинается только когда один из потоков освободился;
- вызываются **методы разных объектов**: `Calculator::Factorial(n)` (с параметром) и `Greeter::Hello()` (без);
- после `Wait()` все результаты посчитаны, после деструктора все потоки завершены.

## 6. Вопросы и ответы

**Что такое пул потоков и зачем он нужен?**
> Заранее созданный набор потоков, которые ждут задачи. Создание потока — дорогая операция
> для ОС, поэтому потоки создаются один раз и переиспользуются для многих задач.

**Что такое критическая секция / мьютекс?**
> Объект, который пускает в участок кода только один поток. Здесь он защищает очередь задач:
> если два потока одновременно вызовут `tasks.pop()`, структура данных сломается.

**Что такое условная переменная?**
> Объект, на котором поток может спать, пока не наступит событие. `SleepConditionVariableCS`
> атомарно отпускает критическую секцию и усыпляет поток, а при пробуждении снова захватывает её.
> `WakeConditionVariable` будит один поток, `WakeAllConditionVariable` — все.

**Почему задача выполняется без блокировки мьютекса?**
> Иначе пока выполняется одна задача, остальные потоки не смогли бы взять следующую —
> параллельности бы не было.

**Как достигается переносимость?**
> Платформенный код изолирован в слое `os::`; нужная ветка выбирается макросом `_WIN32`,
> который определяет компилятор под Windows. Класс `ThreadPool` от ОС не зависит.

**Как передаётся «метод некоторого объекта»?**
> Указателем на метод: `void (T::*method)(A)`. Шаблонный `Run` сохраняет объект, указатель
> на метод и аргумент в лямбде `[obj, method, arg]() { (obj->*method)(arg); }`.
